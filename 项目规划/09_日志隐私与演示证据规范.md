# 日志隐私与演示证据规范

版本：v1.0　｜　日期：2026-11-11　｜　状态：规划，日志功能、保护措施和真实证据尚未实现

本文件细化 [项目规范](01_项目规范与目录约定.md)、[输入规则](08_输入与自动选择规则.md) 及 [PyQt5界面规划](07_PyQt5界面框架与交互规划.md)。目标是准确记录每次生成请求，并用可追溯、非敏感的真实运行材料证明功能。

“只存本地”“忽略Git”“脱敏”等描述在代码和配置实际落地前都属于待实施措施。本轮仅编写规划，不宣称已配置日志、修改忽略规则、录制演示或完成CI。

内存对象、LogStatus、分析/保存异常和公共修改责任以 [10_公共接口与修改权限规范.md](10_公共接口与修改权限规范.md) 为细化依据。timestamp在QRRequest内为带时区datetime，写本CSV时转ISO 8601；options与mode/capture_steps等明确选择合成user_options，不能把原对象直接字符串化冒充JSON。

## 1. GitHub暂定方案与正式提交的关系

用户已决定**当前开发仓库暂用GitHub**。团队可以在GitHub分支、Pull Request和现有仓库历史中推进工作；四人的真实分工继续待定。

正式PDF第4、6、11页仍要求学校私有CSGitLab、个人分支、合并main、GitLab CI以及相应提交材料。当前GitHub决定不等于学校已豁免这些要求，最终对接方式需在提交前落实。

| 对象 | 当前约定 | 最终需要保留/落实 |
|---|---|---|
| 开发历史 | GitHub为当前工作库 | 后续对接学校仓库时保留完整Git提交、作者和分支；不只复制最终文件而丢掉历史 |
| 评审 | 当前用GitHub PR | 记录真实评审；正式材料按实际学校仓库提供要求的合并链接 |
| CI | GitHub Actions可作为辅助，若后续采用 | 不能把Actions截图标成GitLab CI；正式要求仍需真实GitLab流水线 |
| 仓库权限 | 由团队核对当前可见性与访问者 | 私有仓库也不放真实用户输入日志、密钥或无关个人信息 |
| 演示文件 | 仅推送审查过的非敏感证据 | 保证评分者能访问，链接和代码版本正确 |

本轮未查询或改变GitHub可见性、远程配置和学校平台设置。学校材料提交要求仍在 [05_作业要求汇总.md](05_作业要求汇总.md) 中原样保留。

## 2. 四类数据分开管理

| 类别 | 内容/用途 | 建议位置 | 入Git策略 |
|---|---|---|---|
| 使用日志 | 每次接受请求的原文、参数、生成结果；供pandas分析 | `data/usage/qr_usage.csv` | 不提交真实运行日志 |
| 编码轨迹 | 真实位串、码字、矩阵和步骤；供可视化 | 当前QRResult内存 | 默认不自动持久化；选定演示另导出 |
| 技术诊断 | 错误码、模块、时间、必要诊断 | `data/diagnostics/` | 不提交；默认不记输入全文 |
| 演示证据 | 选定的非敏感输入运行所得截图、日志、图像、录屏和CI证明 | `evidence/` | 审查后提交或使用可访问受控链接 |

日常图片在 `outputs/`，一般不入库；要证明评分要求时复制所需成果到evidence并说明来源。不得把“使用日志”与“编码轨迹”混成同一个CSV，也不让所有用户输入都自动进入评分证据。

## 3. 生成前的告知与数据范围

使用日志扩展接入后，生成前在GUI输入区/Information和CLI说明：本机将保存本次输入全文、时间、ID、参数和成功/失败状态，用于历史统计；告知路径和清除方法，提醒使用非敏感文本。

- 用户不接受记录说明时可不提交请求；不能声称“不存文本”却写完整CSV。
- 最终日志扩展开启时，接受的baseline和extended请求都按统一规则记录，不能仅挑成功或只挑扩展请求。
- Stage1/2日志扩展尚未接入时，界面说明实际状态；五份编码步骤demo仍必须提供。
- 不额外采集姓名、账号、IP、设备指纹、剪贴板历史或目录扫描结果；学号只用于作业要求的作者与文档归属，不塞进每条使用日志。
- 原文、QR图、位串、码字和可逆中间数据都可能包含同一内容，保护范围不能仅限输入框。

这是应用行为和数据说明，不代表自动完成了访问控制或磁盘加密。首版不承诺加密CSV，部署在个人/机房账户实际可写目录内，遵守该账户的文件权限。

## 4. 什么算“一次请求”

| 行为 | 新request_id | 使用日志记录 |
|---|---|---|
| 点击Generate并被服务接受 | 是 | 一次完成后记录一条，成功/失败均记录 |
| 显式重新生成相同文本 | 是 | 新请求，另记一条 |
| 空输入/不支持字符/容量不足的已接受提交 | 是 | 失败记录，原文保留，参数按实际解析进度填写 |
| 只改草稿、选参数 | 否 | 不记 |
| 忙状态下忽略重复点击 | 否 | 不记；它没有成为新的接受请求 |
| 查看步骤、切换页签、刷新分析 | 否 | 不记 |
| 保存已有图像或取消保存 | 否 | 不记新的生成请求；IO结果单独反馈 |
| 无法构成正常请求的内部类型错误 | 不强造正常请求 | 诊断记录，不强制把任意对象转为原文 |

同一request_id只追加一次。由共享服务调用UsageLogger，GUI/CLI不各自再写一条。重试失败的日志写入沿用原ID；用户主动发起新生成则新ID，不能以“文本相同”为由合并两次真实请求。

## 5. 使用日志字段和空值

| 字段 | 类型/格式 | 规则 |
|---|---|---|
| `schema_version` | 字符串，如1.0 | 记录格式版本，变化时明确迁移 |
| `timestamp` | 带时区ISO 8601 | 请求接受时间；建议统一UTC存储 |
| `request_id` | UUID字符串 | 请求唯一键 |
| `text_content` | 字符串 | 输入全文，保留空格/换行/逗号/引号，不改成哈希替代必需字段 |
| `source` / `mode` | 枚举 | cli/gui、baseline/extended |
| `requested_version` | 1/2/auto | 用户请求值 |
| `requested_ecc_level` | L/M/Q/H/auto | 用户请求值 |
| `requested_mask_id` | 0..7/auto | 用户请求值 |
| `version` | 可空整数 | 仅已解析可用plan时填写 |
| `ecc_level` | 可空字符串 | 实际解析等级，未解析留空 |
| `mask_id` | 可空整数 | 真正选定/应用的掩码，0有效 |
| `user_options` | JSON字符串 | 允许列表中的选项，键序稳定；不放任意对象或控件 |
| `generation_success` | 明确布尔值 | CSV统一true/false，不用非空字符串的真假推断 |
| `error_code` | 可空字符串 | 成功留空；失败保留生成错误码 |
| `selection_policy_version` | 字符串 | 如input_rules_v1，便于解释自动选择变化 |

作业规定的时间、ID、文本、版本、ECC、mask、用户选项、成功状态必须保留；其他字段是本组为了可追溯性的建议补充。

成功时实际字段完整。字符/容量失败而plan未选出时，实际字段留空，请求值仍保留；若plan已确定、后续内部失败，则保留已解析部分，未选mask留空。不能把请求Auto或默认L/0当作已经成功执行的实际结果。

`text_content=""`是空输入失败的真实内容，不能当作记录缺失；实际数值字段的空单元格表示未解析。读取程序按字段定义区分，不使用一个全局“空值替换”处理所有列。

### pandas读写的关键规则

- UTF-8 CSV，使用规范CSV读写/引用规则，不用手工逗号拼接；多行文本是一个引用字段，不用物理行数统计请求数。
- 显式保留文本/ID/选项等字符串；避免默认NA推断把原文 `NA`、`NULL`、`nan` 变为空值，或把 `00123` 变数字。可采用文本列显式dtype、关闭默认NA推断后，再对实际数值列按schema转换。
- 版本/mask用可空整数，状态严格解析true/false；禁止将字符串 `"false"` 直接作为Python真值。
- UTC存储后在明确标注的时区显示/分组；建议本项目默认显示Asia/Shanghai，可按演示环境调整标签，不能把混合时区字符串直接按日期切片统计。
- Excel用的可分享导出另作安全副本，处理公式前缀，说明转义；原始日志不因导出被静默改写，也不默认以Excel打开用户文本。

## 6. 写入、失败与统计真实性

首版限定一个应用进程写同一个使用日志，服务串行组织请求，进程内保护写入；不宣称支持多进程同时追加或具备数据库事务保证。

追加前校验已有schema，按request_id防重，失败返回明确LogStatus。坏表头、截断记录、损坏JSON或无法解析的文件应提示并保留原件，不自动覆盖/清空。需要修复时复制留证后由用户明确处理，不能为恢复绿灯抹掉失败历史。

| 情况 | 用户与数据处理 |
|---|---|
| QR成功，日志成功 | 展示成功QR与记录状态 |
| QR失败，日志成功 | 展示生成失败与已完成轨迹，记录该失败 |
| QR成功，日志失败 | QR保留，持续提示记录未保存，统计不声称已包含该请求 |
| QR失败，日志也失败 | 同时说明两种问题，不用日志错误覆盖原生成错误 |
| PNG保存失败 | 不修改generation_success，不增加生成请求 |
| 程序异常中止 | 不保证未完成请求必有完整CSV记录；下次读取发现损坏要报告，不伪造补写 |

统计以持久化、schema有效并按ID去重的记录为基础：成功率=成功生成记录数/接受并已记录请求数。显示样本数、筛选和时区；日志写入失败期间不能声称图表覆盖全部真实尝试。

若同一ID有完全一致副本，可告警并去重；若内容冲突，应报告数据不一致，不能任取一条。非法记录不悄悄进入成功率，需说明排除数量或先阻止分析直到修复。

## 7. 保存、清除与Git边界

| 数据 | 生命周期 |
|---|---|
| 当前草稿/结果/轨迹 | 默认仅当前进程；退出后不假装已持久化；不无限积累全部快照 |
| 使用CSV | 退出后保留，直到用户明确清除；首版不承诺自动过期清理 |
| 诊断文件 | 仅留排障所需信息，问题解决后按团队规则清理，不复制到评分材料 |
| 非敏感验收证据 | 保留版本、代码关联与哈希，直到评分/复核流程结束前不随意删除 |
| 备份/导出 | 独立副本，清除当前CSV不会自动删除其他副本或Git历史 |

Clear input仅清草稿；Clear history若提供，应显示目标路径和影响，确认后只操作明确的本项目日志文件，不递归清理任意目录。清除后统计为空，不能继续显示旧数据冒充当前日志。

建议后续给 `.gitignore` 增加 `data/usage/`、`data/diagnostics/`、`outputs/`、`tmp/`；不使用 `*.txt` 或 `*.csv` 全局忽略，以免漏掉demo、依赖和经过审查的证据。**目前这些新增忽略规则尚未实施。**

忽略规则不移除已经跟踪的文件，不保护剪贴板、云盘或既有备份。提交前同时检查暂存清单和证据内容，不只确认文件夹名称。若误传真实敏感数据，应停止继续传播并检查远程/历史/副本；不能声称删除当前文件就清除了全部历史。

## 8. 演示证据采用真实、非敏感输入

证据必须由实际应用/测试/CI产生。规划图、预期表、手填结果、外部生成器图不能当作本项目已经运行的证据。采用固定的作业测试字符串和非敏感边界输入；若统计采用测试数据集，明确标“测试数据”，不要称真实用户行为。

### 8.1 特别重要的脱敏规则

QR本身可以还原原文，位串/码字/部分中间数据也可能还原。**只遮住输入框、保留完整QR，并不等于脱敏。** 最稳妥的办法是在相同代码版本，用安全测试文本重新运行并录制，而不是对含敏感信息的运行材料局部打码后提交。

手机扫码画面要避免通知、聊天、相册、个人账号和无关屏幕；仓库凭据、令牌和敏感绝对路径不出镜。必要裁剪/遮挡不能掩盖关键错误，也不能改变QR模块后继续声称这是成功扫码用的原图。保留原始非敏感素材与经过说明的展示副本。

### 8.2 证据目录

```text
evidence/
  README.md                         # 实际证据入口、场景和最终有效版本
  manifest.csv                      # 每个制品的路径、来源、commit、哈希等
  stage_1/
    demo_1.txt ... demo_5.txt        # 固定baseline；包含合理失败及失败前步骤
  stage_2/
    <case_id>/                      # GUI、Information、保存、真实手机扫码
  individual/
    <student_id>/<case_id>/          # 真实学号确认后创建
  integration/
    <case_id>/                      # 同一应用四项扩展共同运行
  ci/
    github/                         # 若使用Actions，明确平台
    gitlab/                         # 正式要求的真实GitLab流水线
```

目录是待建规划，本次不创建空证据或伪造日志。每份最终README/个人文档通过相对链接指向实际存在、可访问的材料。

## 10. 每个制品应记录的元数据

| 字段 | 含义 |
|---|---|
| `case_id` / `requirement_ids` | 场景和覆盖要求，如B08/G08/E02 |
| `artifact_path` / `artifact_type` | 相对路径、txt/png/mp4等 |
| `input_id` / `request_id` | 固定测试输入标识、本次实际请求ID；无请求的CI证据可空 |
| `expected` / `actual` / `conclusion` | 预期、真实结果、通过/失败，不预先填通过 |
| `code_commit` / `branch` | 被演示和测试的完整代码SHA及分支 |
| `source_dirty` | 是否有未提交源码变更；存在则说明，不能把SHA当成全部运行代码 |
| `captured_at` / `operator` | 带时区实际采集时间及真实操作者，个人归属按要求确认 |
| `environment` | 实际Python、PyQt5/Qt、依赖、OS、DPI及必要扫码设备信息 |
| `interface_version` / `rule_version` / `log_schema` | 如接口契约1.0、input_rules_v1、CSV schema版本，分别追溯 |
| `sha256` | 制品最终字节的哈希；生成后计算，禁止填假值 |
| `related_ci` | 对应平台/运行链接，没有则如实留空 |
| `privacy_review` / `notes` | 使用安全输入、裁剪说明、局限与待修复项 |

可用manifest.csv记录并在evidence/README用表格解释。manifest不包含自身文件的哈希，避免自引用；证据提交可晚于代码提交，`code_commit`必须指向实际运行的源码版本。之后只改证据说明不等于代码变了，但若业务代码变化，受影响场景应重新录制/验证。

规划阶段的模板统一标“待填写/模板”，不产生看似真实的pipeline号、时间戳、操作者、commit或测试通过截图。

## 11. 采集、命名和发布步骤

1. 选择已知非敏感场景和输入，核对代码版本/源码未提交修改情况。
2. 运行实际程序或测试，保留失败和已完成步骤，不手工补齐结果。
3. 截图/录屏体现操作、输入、实际参数、结果及必要错误说明；关键集成段保持连贯，剪辑处说明。
4. 扫码场景用手机实际识别并比对，说明是否从窗口或导出图识别。
5. 记录环境、预期/实际、版本与限制；收集真实CI链接和状态。
6. 检查QR及可逆数据、屏幕内容和账号等是否暴露不应分享的信息；优先用安全输入重录。
7. 确定制品版本、计算哈希、更新索引和文档链接，再纳入当前GitHub提交或受控演示链接。
8. 最终对接学校GitLab、权限、GitLab CI和提交归档时，复核证据仍可访问且与代码一致。

命名建议：`YYYY-MM-DD_<case_id>_<short_code_sha>_v01.png/mp4/txt`。五个指定基础文件仍保留demo_1.txt至demo_5.txt的清晰入口；若修订，可把旧版放明确的历史子目录，README指向最终有效版本，不丢失失败/复验历史。

Git保存版本和作者历史，SHA-256校验制品字节，两者不能互相替代。录屏过大时先核对课程平台限制，使用评分者可访问的受控链接，不能默认为上传任意公共视频站，也不能把只对本人可见的链接写成已交付。
