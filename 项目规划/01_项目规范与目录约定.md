## 2. 命名规则

| 对象 | 规则 | 示例 |
|---|---|---|
| Python 包、模块 | 英文小写 snake_case；避免空格和连字符 | `mask_selector.py` |
| 函数、变量、参数 | snake_case，名称表达业务含义 | `choose_best_mask`、`data_capacity_bits` |
| 类、数据结构 | PascalCase | `QRRequest`、`MaskSelection` |
| 常量 | UPPER_SNAKE_CASE | `SUPPORTED_VERSIONS` |
| 测试 | 文件和函数以 `test_` 开头 | `test_mask_preserves_function_modules` |
| 个人反思 | 【硬性】8 位真实学号 | `individual_<student_id>.md` |
| 分支 | `feature/<student_id>-<topic>` | `feature/<student_id>-mask-selection` |
| 修复分支 | `fix/<topic>` | `fix/format-placement` |
| 会议记录 | `YYYY-MM-DD_meeting_<nn>.md` | `2026-11-10_meeting_01.md` |
| 决策记录 | `adr_<nn>_<topic>.md` | `adr_01_gui_framework.md` |
| 图像/录屏证据 | 日期、阶段、场景、短commit、版本 | `2026-12-16_stage2_scan_<sha>_v01.png` |
| 运行输出 | 唯一request_id，不用用户原文作文件名 | `qr_<request_id>.png` |
| 发布标签 | `v<major>.<minor>.<patch>` | `v0.1.0` 基础、`v0.2.0` 界面、`v1.0.0` 最终 |
| 提交归档 | 【硬性】对应 Blackboard 组号 | `Group-A01.zip`，实际换成本组编号 |

文档可用中文命名；Python 代码与机器处理的路径使用英文。日期用 ISO 格式，日志时间使用带时区的 ISO 8601。所有文本采用 UTF-8；Python 4 空格缩进；换行统一 LF。Git 建议记录 `.gitattributes` 的文本换行规则，不对 PDF/图像作文本转换。

## 3. 存储与版本规则

| 类别 | 是否入库 | 规则 |
|---|---|---|
| 作业原件 | 保留本地原件；是否入校内仓库按课程规则决定 | 不修改；不重复上传到公开仓库 |
| 代码、测试、CI、规划 | 是，规划能否进入最终归档另按提交规范处理 | 每次有效变化可追溯 |
| 容量与参考表 | 是 | 标明来源、版本范围、单位及抄录核查人 |
| 评分证据 | 是；视频超出平台限额时用受控链接 | 只用非敏感演示输入，附说明与代码版本 |
| 用户运行日志 | 否 | `data/usage/`，限制本地访问，告知会记录文本 |
| 一般输出和临时文件 | 否 | `outputs/`、`tmp/`，需保留的复制至 evidence 并说明 |
| 缓存、虚拟环境、密钥 | 否 | `__pycache__/`、`.venv/`、`.env` 等忽略 |

建议在现有 `.gitignore` 上新增 `outputs/`、`data/usage/`、`tmp/`、`*.log` 等规则；本次规划不修改根目录配置。不要用广泛的 `*.txt` 忽略规则，以免漏交五个演示文件和依赖文件。

个人工作只修改自己的功能分支；不创建 `final_final.py`、`new2.py` 等副本。历史版本交给 Git 管理，已验收的证据保留 `v01/v02` 和对应 commit，不覆盖旧版而丢失历史。README 指向最终有效版本。

开发与 CI 均使用临时路径测试读写；不得将 CI 测试数据追加到真实用户日志。截图和导出日志时先核查个人信息、令牌、仓库凭据及敏感输入。

## 4. 数据、编码与错误规范

1. 输入不自动 `.strip()`、转小写或替换字符。五个指定字符串本身无首尾空白；用户实际输入中的空白应保留，若不支持则明确拒绝。
2. Byte Mode 默认使用 ISO-8859-1，按编码后的字节数校验容量，不按屏幕字符数或 UTF-8 字节数猜测。
3. 不支持字符、容量不足、参数错误都给出可理解的错误；禁止 `errors='ignore'`、截断文本或悄悄切换编码。
4. 基础模式始终为 V1/L/Mask0，扩展不得改变基础演示的可重复性；扩展模式显式启用自动或手动参数。
5. 矩阵主体不含 quiet zone；数据值仅为 0/1。保留区用独立布尔矩阵表示，不能用负值哨兵混入最终矩阵。
6. 渲染统一增加至少 4 模块白色 quiet zone、使用最近邻显示、保持正方形比例，避免插值灰边或透明背景破坏扫码。
7. 错误结果保留已完成的 TraceStep 和明确错误码；不把失败当作成功，不输出残缺二维码供用户误用。
8. 非预期错误在服务边界转为安全说明；详细堆栈仅进入本地诊断，演示与用户界面不暴露路径或凭据。

## 5. 接口与注释约定

数据结构和函数接口详见 [架构规划](02_系统架构与接口规划.md)，它是接口的单一约定来源。

- 核心模块不能导入 GUI、matplotlib、pandas；也不直接写日志或文件。
- 只有展示层持有界面控件。个人扩展接收普通数据，不接收界面对象。
- 使用类型标注和 docstring 描述输入、返回值、异常、单位、是否修改输入。复杂格式位和落位步骤注明规范来源。
- 每个个人扩展模块写真实姓名/学号、负责范围、关键接口；修改别人的模块时记录作者与修改目的，并保留正常 Git 历史。
- 注释解释原因、规范依据和边界，不堆叠对语句表面含义的重复说明。
- 容量、ECC 分块数、码字数按规范表管理，不散落为难以追踪的魔法数字。
- 不为展示三种范式强行复杂化：核心纯函数体现函数式，编排/循环体现命令式，TraceVisualizer/UsageLogger 等有状态对象体现面向对象；最终引用实际代码证明。

## 6. Git、评审与 CI

【硬性要求】学校私有 GitLab 仓库，组员 Maintainer，各有个人分支，最终合并 main。

【当前平台决定】用户暂用GitHub组织开发；当前评审称Pull Request，学校GitLab对应Merge Request。后续落实正式仓库/CI要求时保留提交、作者、分支和证据来源，不把GitHub Actions当作GitLab CI。见 [09_日志隐私与演示证据规范.md](09_日志隐私与演示证据规范.md)。

【建议方案】每个变更以小任务开发。开始前同步 main；提交格式用 `feat: ...`、`fix: ...`、`test: ...`、`docs: ...`。PR/MR至少说明问题、变化、影响接口、测试和证据，并由一位其他成员评审。禁止强推共享 main；分支清理需确认历史已保留。

公共文件负责人负责协调，不意味着其他人不能修改。修改 `models.py`、`service.py`、资源表和 CI 时先通知负责人，通过 MR 说明接口影响。所有权见四人分工表。

CI 至少有 lint 与 test 两个阶段；使用课程允许的 lint 工具及标准库 `unittest`，保持 Python 3.13.9 与教学机房一致。测试命令建议为 `python -m unittest discover -s tests -v`。不得标记关键测试为允许失败来伪造绿灯。

个人扩展每人至少 3 个非平凡测试；本组以至少 12 个扩展测试为最低计划，另设基础与集成测试。测试应有独立期望值或不变量，不能用同一被测函数生成“标准答案”。具体测试设计见验收清单。

## 7. 环境与依赖

依赖表需记录包名、已验证版本、用途、作业/课堂/审批来源、Python 兼容性。用户已确认课堂使用PyQt5，采用其作为桌面GUI框架；具体版本与教学机房兼容性仍须验证，lint工具仍待核实。未获许可的二维码生成/解码库不能替代自编核心。页面、控件和环境验证见 [07_PyQt5界面框架与交互规划.md](07_PyQt5界面框架与交互规划.md)。

README 必须从干净教学机房环境说明配置与启动，不依赖个人绝对路径、不要求读者已有本人的 conda 环境、不依赖管理员权限下的隐藏安装。CLI 与 GUI 入口名建议分别为 `main_cli.py`、`main_gui.py`；命令及参数待实现后写成经过验证的内容。

## 8. 文档与会议记录

输入/空白/容量/默认与自动选择的细化规则见 [08_输入与自动选择规则.md](08_输入与自动选择规则.md)。使用日志、pandas空值处理、隐私、Git忽略待办和演示制品追溯见 [09_日志隐私与演示证据规范.md](09_日志隐私与演示证据规范.md)。细化规则与已有概括存在歧义时，先对照作业原文再统一修订，不能让各模块自行选择不同解释。
